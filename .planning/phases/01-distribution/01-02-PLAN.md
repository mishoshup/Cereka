add_custom_command(TARGET CerekaLauncher POST_BUILD

With:
```cmake
if(WIN32)
    add_custom_command(TARGET CerekaLauncher POST_BUILD
        COMMAND Qt6::windeployqt
        ARGS --compiler-runtime $<TARGET_FILE:CerekaLauncher>
        COMMENT "Bundling Qt6 DLLs + compiler runtime for distribution"
    )
endif()
```

The `--compiler-runtime` flag instructs windeployqt to locate the compiler's runtime DLLs (libc++.dll and libunwind-1.dll for the llvm-mingw toolchain) by finding the compiler in PATH, then copying them alongside the Qt DLLs. This requires the llvm-mingw toolchain bin/ directory to be in PATH at the time the POST_BUILD step runs on Windows.

The WIN32 guard prevents CMake configure errors on Linux where Qt6::windeployqt is not available as a CMake imported target.

Do not modify anything else in launcher/CMakeLists.txt.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | windeployqt PATH-based DLL discovery | accept | windeployqt runs at developer build time on a trusted developer machine. The runtime DLLs it copies (libc++.dll, libunwind-1.dll) are from the llvm-mingw toolchain — attacker would need to compromise the build machine. This is a build-time tool, not a runtime security boundary. |
| T-02-02 | Spoofing | Missing --compiler-runtime fallback | accept | If --compiler-runtime fails silently (toolchain not in PATH), the launcher simply ships without runtime DLLs and fails on fresh machines. This is a packaging quality issue, not a security issue. Low risk — documented in RESEARCH.md pitfall 4. |
